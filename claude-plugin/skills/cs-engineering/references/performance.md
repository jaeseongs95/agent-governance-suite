# 성능

모듈 `performance` · v0.1.0 · 상태 `validated`



검증 범위: 핵심 규칙의 제한된 실행 참조 사례를 로컬에서 검사했다. 실제 대상의 구현 검증과 독립 감사는 별도다.



## PERF-MEASURE-001 — 비교 가능한 성능 계측

**원리:** 기능 정확성을 유지한 동일 조건의 비교를 먼저 고정한다.

**불변조건:** 측정 대상·부하·환경·따뜻한 캐시 여부가 추적 가능하다.

**적용 조건:** 속도·비용·캐시 개선을 주장한다.

**가정:** 요청과 허용된 대상의 실제 코드·운영 경계가 확인되어 있다.

**실패 형태:** 작은 입력·warm cache만 비교해 전체 성능 향상으로 광고한다.

**판단 질문:** median과 tail은 어떻게 다른가? / 처리량·오류율·메모리는 함께 측정하는가?

**검증 의무:** baseline과 후보를 동일 부하에서 반복 측정하고 원시 결과·환경을 보존한다.

**하지 않을 일:** 출력 없는 microbenchmark를 제품 성능이라고 부르지 않는다.

**출처 식별자:** AGS-DESIGN (`assets/sources.json`에서 범위와 원문 위치를 확인한다.)



## PERF-BOUND-002 — 백프레셔와 상한

**원리:** 대기량·동시성·메모리·재시도를 유한하게 만든다.

**불변조건:** 포화 시 정의된 거절·지연·드롭 동작으로 자원 상한을 유지한다.

**적용 조건:** 입력이 처리 속도보다 빨라질 수 있다.

**가정:** 요청과 허용된 대상의 실제 코드·운영 경계가 확인되어 있다.

**실패 형태:** 모든 요청을 무제한 Promise·큐에 쌓는다.

**판단 질문:** 생산자를 느리게 할 수 있는가? / 버퍼 상한의 단위는 개수인가 바이트인가?

**검증 의무:** 지속 과부하에서 queue depth·memory·오류 응답·부하 해제 후 회복을 측정한다.

**하지 않을 일:** Node highWaterMark를 모든 메모리의 강한 전역 상한이라고 하지 않는다.

**출처 식별자:** NODE-STREAMS (`assets/sources.json`에서 범위와 원문 위치를 확인한다.)



## PERF-CACHE-003 — 캐시 정합성과 수명

**원리:** 캐시가 틀릴 수 있는 조건과 퇴거 조건을 명시한다.

**불변조건:** 허용된 신선도 범위와 메모리 상한을 함께 지킨다.

**적용 조건:** 계산·조회 결과를 캐시한다.

**가정:** 요청과 허용된 대상의 실제 코드·운영 경계가 확인되어 있다.

**실패 형태:** TTL만 두고 고유 키가 계속 들어와 만료 전 메모리가 무한 증가한다.

**판단 질문:** 권한·버전·지역이 키에 포함되는가? / 무효화 실패와 stampede는 어떻게 다루는가?

**검증 의무:** 변경·만료·충돌·동시 miss·많은 고유 키를 넣어 정합성과 상한을 검사한다.

**하지 않을 일:** 성능을 위해 사용자별 권한 경계를 섞지 않는다.

**출처 식별자:** AGS-DESIGN (`assets/sources.json`에서 범위와 원문 위치를 확인한다.)



## PERF-BATCH-004 — 배치와 지연 절충

**원리:** 처리량 개선과 대기 지연·실패 범위를 함께 평가한다.

**불변조건:** 배치는 부하에 맞춰 제한되며 저부하에서도 최대 대기 시간을 넘기지 않는다.

**적용 조건:** 요청·메시지·DB I/O를 묶어 처리한다.

**가정:** 요청과 허용된 대상의 실제 코드·운영 경계가 확인되어 있다.

**실패 형태:** 항상 세 개가 모일 때까지 기다려 마지막 한 요청이 영구 대기한다.

**판단 질문:** 개수·바이트·시간 상한은 있는가? / 일부 실패를 개별 결과로 돌려주는가?

**검증 의무:** 저부하·고부하·큰 항목·부분 실패·종료 flush를 측정한다.

**하지 않을 일:** 항목 수나 10KB 같은 임의 고정값을 근거 없이 표준화하지 않는다.

**출처 식별자:** AGS-DESIGN (`assets/sources.json`에서 범위와 원문 위치를 확인한다.)
