# 사용하기

AGS를 설치한 뒤 평소처럼 에이전트에게 일을 맡기면 됩니다. 이 문서는 요청하는 법, 설치하면 달라지는 동작, workflow와 편집 관문, 작업 기록, 하위 작업의 모델 선택, AGS가 보장하지 않는 것을 설명합니다. 설치는 [README](../../README.md#설치)를 봅니다.

## 요청하는 법

원하는 결과와 확인할 조건, 바꾸면 안 되는 대상을 함께 알려 주십시오. 모든 요청에 스킬이나 workflow를 직접 지정할 필요는 없습니다. 에이전트가 요청 목적과 스킬의 적용·제외 조건을 대조하고, 단계가 이어지는 변경에는 workflow를 씁니다. 질문·설명이나 전문 스킬 하나로 끝나는 일은 그 범위에서 처리합니다.

```text
이 안내문을 처음 방문하는 사람이 예약까지 진행할 수 있게 고쳐 줘.
예약 조건과 연락처는 보존하고, 바꾸기 전에 확인할 사례를 적어 줘.
실제로 확인한 것과 사람의 확인이 남은 것을 나눠 알려 줘.
```

```text
이 기능을 구현하고 검증해 줘. 수정 범위와 완료 기준을 먼저 정리하고,
최종 결과에는 실제로 실행한 검사와 아직 해결하지 못한 문제를 함께 적어 줘.
```

스킬을 직접 지정하려면 호스트의 스킬 호출 방식으로 이름을 적습니다. 예를 들어 Codex에서는 `$orchestrator`, Claude Code에서는 `/agent-governance-suite:orchestrator`입니다.

## 설치하면 달라지는 것

AGS는 MCP 서버(도구)와 호스트 hook(시점별 안내와 관측)으로 동작합니다. 안내가 있다는 사실만으로 에이전트가 지시를 따랐거나 결과가 검증됐다고 볼 수는 없습니다.

| 시점 | AGS의 동작 |
| --- | --- |
| 세션 시작·재개·압축 | 스킬 선택과 workflow 사용 기준을 안내하고, 전역·담당·상황 컨텍스트를 넣습니다. 재개·압축 뒤에는 현재 작업 기록 본문을 넣으며, 본문이 필요하면 에이전트가 `load_context`로 읽습니다. |
| 사용자 메시지마다 | 턴 확인 안내와 설치된 스킬별 대상 목록으로 스킬 선택을 다시 살피게 합니다. 교정·결정·승인·금지·남은 일을 `checkpoint_context`에 저장하라는 안내도 들어 있습니다. |
| 서브에이전트 시작 | 스킬 대상 목록과 맡은 범위·금지 구역·쓰기 소유를 지키라는 안내, 전역·담당 컨텍스트, 부모 세션의 상황 컨텍스트를 넣습니다. Claude Code·Codex는 서브에이전트 시작 hook으로 넣습니다. Antigravity에는 이 시작 hook이 없어, agy 서브에이전트는 AGS 도구를 처음 호출한 다음 단계부터 담당 컨텍스트를 받습니다. |
| workflow가 바뀔 때 | AGS 도구 응답에 다음 단계와 스킬 대조 안내를 붙입니다. |
| 작업 단계 경계 | 세션 도중 바뀐 전역·담당·상황 컨텍스트가 있으면, 그 판을 아직 받지 않은 실행 주체에게 한 번 넣습니다. |
| 파일을 바꿀 때 | 편집 대상 경로를 workflow 범위와 대조합니다(아래 「편집 관문」). |
| 턴·서브에이전트 종료 | 제품 파일을 고친 뒤 통과하지 못한 workflow 단계가 남으면 이어 갈 일을 안내합니다. 확인은 일한 실행 주체별로 합니다. 서브에이전트의 편집과 그 서브에이전트가 시작한 workflow는 그 서브에이전트가 끝날 때(Claude Code·Codex `SubagentStop`, agy 서브에이전트 대화의 Stop) 확인하고, 부모의 턴 종료에서는 확인하지 않습니다. |

## workflow와 편집 관문

단계가 이어지는 변경 작업은 workflow로 시작합니다. 에이전트가 `start_workflow`에 목표·단계·쓸 스킬(`skills`)·수용 기준·바꿀 경로(`writeTargets`)를 주면, 서버가 계획·root·lease·run을 한 번에 만듭니다. 스킬은 하나 이상 이유와 함께 내야 하고, 시도마다 따로 내므로 상황이 바뀌어 다시 시작할 때 스킬도 다시 정합니다. JEV 같은 조언을 받았으면 그 작업 ID를 함께 내어 조언과 실제 선택의 차이를 run에 남기며, 조언이 없어도 시작은 막히지 않습니다. 한 세션은 겹치지 않는 경로로 workflow를 여러 개 함께 진행할 수 있습니다. 각 단계 결과는 `record_stage_result`로 기록하고, 모든 계획 단계가 통과하고 미해결 항목이 없을 때만 `finalize_workflow`가 완료 결과를 만듭니다. 기록상 완료는 제출 내용이 사실이라는 증명이 아닙니다.

**편집 관문**은 호스트가 알려 준 편집 대상 경로를 진행 중인 workflow 범위와 대조합니다.

- workflow 없이 바꾼 제품 파일과 진행 중 workflow의 범위 밖 제품 파일을 workflow 시작부터 턴 종료 검사 사이 구간에서 셉니다. 서로 다른 세 번째 파일을 바꾸는 호출부터 거부합니다.
- 버전 관리 밖 파일은 이 세 파일 한도에서 빠집니다. OS 임시 폴더, 호스트의 에이전트 메모 폴더, 관리자 페이지나 `AGENT_GOVERNANCE_PHASE_EXEMPT_PATHS`로 정한 예외 경로도 세지 않습니다.
- 검토·사용자 판단을 기다리는 root의 대상에는 별도 거부가 적용됩니다.
- 거부되면 거부 문구의 예대로 `start_workflow`를 호출합니다. 진행 중인 작업과 다른 일이면 겹치지 않는 `writeTargets`로 workflow를 하나 더 시작합니다.
- 관문은 파일시스템 전체를 감시하지 않습니다. 지원 편집 도구와 셸의 명시적 출력 리다이렉션, 일부 PowerShell 쓰기 경로를 다룹니다. 임의 스크립트·별칭·동적 경로로 생긴 쓰기를 모두 알아내지 못합니다. 경로를 알 수 없는 셸 쓰기는 그 자체로 한 파일로 셉니다.
- AGS 내부 장애로 검사할 수 없으면 편집을 무조건 막지 않고 그 상태를 기록하고 알립니다.

## 작업 기록(상황 컨텍스트)

에이전트는 교정·결정·남은 일을 작업 기록에 저장하고, 재개할 때 원문과 현재 상태를 대조합니다. 작업 기록은 스킬이 아니라 MCP 도구와 hook이 맡습니다.

| 도구 | 하는 일 |
| --- | --- |
| `checkpoint_context` | 압축·재개 뒤 이어 갈 현재 상태(목표, 최신 결정·권한·제약, 미완료·다음 행동, 필요한 실패·근거)를 저장합니다. 본문 전체는 UTF-8 2000 byte 이하입니다. |
| `inspect_context`, `load_context` | 자기 현재 기록과 `stateToken`을 읽습니다. 저장·삭제 때 `expectedStateToken`으로 그 토큰을 대조합니다. |
| `suppress_context_restore` | 자동 복원을 억제합니다. |
| `purge_direct_context` | 사용자가 명시적으로 삭제를 요청할 때 현재 기록만 지웁니다. |

- 작업 기록은 workflow의 단계 원장을 복제하지 않습니다. 저장된 요약이 있어도 실제 파일·환경·시험 결과를 다시 확인해야 합니다.
- 자기 현재 기록은 `load_context`에 `{"schemaVersion":"1.0.0"}`만 보내 읽습니다. 상태가 바뀌어 저장이 충돌하면 최신 기록을 다시 읽어 재구성합니다. 서명된 fork·workflow 후보는 제공받은 `candidateToken`으로 고르지만, 임의의 과거 판·다른 세션의 기록·이력은 조회하지 못합니다.
- 세션 시작·재개·압축 때 넣는 본문은 읽은 시점의 내용입니다. 호스트가 받았다는 확인이 없으므로, 장애 뒤까지 정확히 한 번 전달된다거나 모델의 첫 행동까지 최신이라는 보장은 없습니다.
- 비밀값, 개인정보, 원시 로그·코드를 작업 기록에 넣지 마십시오. 저장 위치와 정리는 [상태 저장과 정리](state.md)를 봅니다.
- 여러 세션이 함께 쓰는 전역·담당 컨텍스트는 [관리자 페이지와 컨텍스트](admin-page.md#전역담당상황-컨텍스트)를 봅니다.

## 스킬을 쓰는 시점

각 스킬은 작업 상황에 따라 검토하거나 호출합니다. 아래 목록은 위에서부터 모두 실행하라는 순서가 아닙니다. 요청의 위험도와 현재 상태에 맞는 스킬만 고르고, 둘 이상을 이을 때는 `orchestrator`가 순서를 정합니다. 스킬 목록은 [README의 스킬 표](../../README.md#스킬)에 있습니다.

- **시작 전:** 파일을 바꾸거나 명령을 실행하기 전에 적용 지침과 저장소 관례를 확인하고, 목표·범위·완료 조건을 정할 때
- **진행 중:** 작업을 독립 단위로 나눌 필요가 생기거나, 실패 비용이 큰 결정을 여러 관점에서 검토할 때
- **수렴 검토:** 반복 시도의 허용 횟수를 다 썼거나 목표·평가 기준·입력이 달라질 수 있어, 새 시도 구간(`epoch`)을 열기 전에 기존 계약과 바뀐 제안의 의미가 같은지 확인할 때
- **변경 전후:** 변경 전에 Git 기준 상태를 기록하고, 변경 뒤 실제 diff를 그 기준과 비교해 범위 밖 파일이 없는지 확인할 때
- **되돌리기 어려운 변경 직전:** 삭제, 배포, 마이그레이션처럼 영향이 큰 동작의 대상·권한·복구 조건을 점검할 때
- **완료 전:** 완료를 선언하기 전에 수용 기준별 근거를 확인하고, 고위험 작업은 독립 감사까지 통과했는지 확인할 때
- **문제가 반복될 때:** 같은 실패가 반복되거나 원인이 불분명할 때 관측과 가설을 나누고 다음 판별 검사를 정할 때
- **복구를 고를 때:** 원인이 확정된 실패의 복구안 2~3개를 비교하고, 새 작업 계약에 결속할 인계 자료를 만들 때
- **평가 전후:** 평가 실행 전에 설계의 실행 가능성을 확인하거나, 실행 뒤 결과·판정·집계 근거의 타당성을 감사할 때

예를 들어 위험도가 높은 배포 작업은 다음처럼 진행합니다.

1. 작업 전에 적용 지침과 저장소 관례를 확인하고, 허용 범위와 완료 조건을 정합니다.
2. 되돌리기 어려운 변경이면 권한, 대상, 영향 범위, 복구 방법을 먼저 점검합니다.
3. 여러 에이전트가 함께 일하면 담당 영역을 나누고 구현자와 감사자를 분리합니다.
4. 변경이 끝나면 처음 정한 범위와 실제 변경을 비교하고 시험 결과를 확인합니다.
5. 감사자와 구현자가 같거나, 감사 대상이 현재 결과와 다르거나, 해결되지 않은 문제가 남아 있으면 완료를 거절합니다.

MCP 서버는 계획 서명, 단계 순서, 단계 결과 형식, 필수 산출물, 감사 대상의 일치, 미해결 항목을 검사합니다. 다만 제출된 근거의 진실성이나 작업자의 실제 신원은 인증하지 않습니다.

## 스킬 선택 조언(JEV)

`classify_skills`는 스킬 분류 조언이 설정된 환경에서만 동작합니다. JEV는 조언 계층이며, 최종 선택은 에이전트가 합니다. JEV를 켜고 설정하는 방법은 [관리자 페이지의 JEV 절](admin-page.md#jev-스킬-선택-조언)을 봅니다.

## 하위 작업의 모델과 추론 수준

`model-effort-advisor`는 **이미 승인된 서브에이전트 작업을 호출하기 전에** 역할·난도·위험·검증 가능성과 품질·속도·비용 선호를 살펴 모델·추론 수준을 고르도록 돕습니다. `economy`, `balanced`, `quality` 선호를 쓸 수 있고 기본값은 `balanced`입니다. 위임할지, 몇 명을 쓸지, 어떤 권한과 감사를 줄지는 이 스킬이 정하지 않습니다. 현재 메인 모델을 관측하거나 UI 설정을 바꾸는 상담 기능도 아닙니다.

- 공통 선택 계약은 벤더와 분리되어 있습니다. 배포 catalog에 있는 조합이라고 해서 현재 호스트에서 쓸 수 있다는 뜻은 아닙니다. 실제 호스트가 제공한 지원 정보와 호출 필드를 먼저 확인합니다.
- 선택한 값, 실제 호출에 보낸 값, 호스트에서 관측한 유효 설정을 따로 기록합니다. 상속 설정을 볼 수 없으면 미확인으로 남깁니다.
- 고위험 작업의 `general`·`high` 이상은 추천 순서일 뿐입니다. 모델 등급·추론 수준 때문에 위임·결과 기록·종결이 거부되지 않습니다. 처음 보는 모델은 등급 미상으로 기록하며 거부하지 않습니다.
- 자세한 내용은 [모델 라우팅과 호스트별 적용](../../skills/coordinate-subagents/references/model-routing.md)에 있습니다.

## 보장하지 않는 것

- **같은 OS 사용자 권한에 대한 보안 경계가 아닙니다.** 그 권한으로 도는 프로그램은 상태 DB를 읽고 바꾸거나 MCP 서버를 직접 호출할 수 있습니다. 제출된 근거·감사자 신원·사용자 승인 참조의 형식과 일관성을 검사해도 진실성을 인증하지는 않습니다. [보안 정책](../../SECURITY.md)
- **편집 관문은 파일시스템 전체를 감시하지 않습니다.** 위 「편집 관문」의 범위만 다룹니다.
- **안내·스킬 호출·도구 성공은 행동 완료와 다릅니다.** 턴 확인 안내는 지시 준수를 강제하지 않으며, 앞서 읽은 스킬 본문을 대화에서 지우지도 못합니다. 위임 규칙은 안내하고, 위임 호출 전체를 검사하지 않습니다.
- **메시지 ACK와 깨우기는 업무 결과나 승인이 아닙니다.** [세션 협업](collaboration.md)을 봅니다.
- **검증 결과는 판·호스트·CLI 버전별로 따로 읽습니다.** hook 출력, MCP 성공 응답, 모델에 실제로 전달된 입력, 실제 준수는 각각 확인해야 합니다. 각 판에서 실행한 검증과 실행하지 않은 검증은 [릴리스 노트](../release-notes/)의 검증 절에 적습니다.
