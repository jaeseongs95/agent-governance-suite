# 세션 협업

같은 컴퓨터에서 같은 OS 사용자로 실행한 AGS 세션끼리 현황판으로 서로를 찾고 PEER 메시지를 주고받습니다. 호스트가 달라도(Claude Code·Codex·Antigravity) 같은 공유 상태 폴더를 쓰면 함께 협업할 수 있습니다. 메시지 상태와 저장 한도의 기술 계약은 [세션 메시지 계약](../contributing/session-messaging.md)에 있습니다.

## 현황판

- `update_session_status`로 이 세션이 지금 하는 일을 한 줄로 적고, `list_session_status`로 다른 세션의 호스트·세션 ID·작업 폴더·한 줄 요약·역할을 봅니다.
- 요청 원문은 저장하지 않습니다. 세션 ID와 작업 폴더는 hook 입력에서 채웁니다.
- 역할은 관리자 페이지에서 서명한 결속이 있으면 그 역할(`roleSource: "signed"`), 없으면 세션이 스스로 적은 역할(`roleSource: "self"`)을 보여 줍니다. 현황판의 역할은 접근 권한이나 실행 승인이 아닙니다.
- 현황판은 다시 읽어야 변경을 알 수 있는 pull 방식입니다. 실행 중인 다른 세션의 작업을 멈추게 하는 채널이 아닙니다.
- 끝난 세션은 요약이 있어도 현황판에 나오지 않습니다.

## 메시지 보내기

에이전트에게 「현황판에서 ○○ 담당 세션을 찾아 PEER 메시지로 검토를 요청해 줘」처럼 요청하면, 에이전트가 다음 도구를 씁니다.

| 도구 | 하는 일 |
| --- | --- |
| `prepare_session_message` | 대상·본문·TTL을 고정하고 시스템이 발급한 `messageId`를 받습니다. 전달 효과는 없습니다. |
| `send_session_message` | 발급받은 `messageId`만 넘겨 전송합니다. |
| `get_session_message_status` | 같은 `messageId`로 전달·ACK 상태를 봅니다. |
| `acknowledge_session_messages` | 받은 쪽이 메시지를 처리했다고 확인합니다. |
| `recall_session_message` | 받는 쪽이 아직 가져가지 않은 자기 메시지를 회수합니다(메일 발송 취소와 같습니다). |

- 메시지는 전송, 본문 전달, 처리 확인(ACK)을 따로 기록합니다. **ACK는 메시지를 처리했다는 확인일 뿐, 작업 완료나 실행 승인이 아닙니다.** 검토 결과와 근거는 별도 메시지로 받습니다.
- 받는 세션이 오프라인이면 보낸 세션은 기다리며 멈추지 않고 답이 필요 없는 일을 계속합니다.
- 결과가 불분명한 메시지를 새 ID로 다시 보내지 않습니다. 같은 `messageId`로 상태를 조회하거나 send를 다시 시도합니다. 새 ID로 보내면 한 의도가 두 메시지로 전달될 수 있습니다.
- 본문은 UTF-8 4096 byte까지입니다. TTL은 30초~24시간이며 기본 1시간입니다.
- 받는 쪽에서 메시지는 도구 경계나 턴이 끝날 때 전달됩니다. 사용자 입력 직후에는 다음 도구 경계 한 번을 미룹니다.

## 쉬고 있는 세션 깨우기

메시지를 넣은 뒤 쉬고 있는 세션을 깨우는 방식은 호스트마다 다릅니다. 깨우기는 「받은함을 보라」는 신호이며, 본문은 깨우기 경로로 보내지 않습니다.

| 호스트 | 기본 동작 |
| --- | --- |
| Claude Code | inbox로 깨웁니다(`claude-inbox`). |
| Codex | 깨우지 않고 다음 경계까지 미룹니다(`codex-deferred`). [queue wake 설정](#codex-queue-wake-설정)을 켜면 대기열로 깨웁니다. |
| Antigravity | 실행 환경 정보(`ANTIGRAVITY_PROJECT_ID` 등)가 있으면 대기열로 깨웁니다(`antigravity-queue`). `AGENT_GOVERNANCE_ANTIGRAVITY_QUEUE_WAKE`로 켜고 끌 수 있습니다. |

`send_session_message` 결과와 `get_session_message_status`, 현황판의 각 세션에는 조언용 `autoWake`가 붙습니다. 받는 세션의 깨우기 경로를 지금 쓸 수 있는지에 대한 사실만 알려 주며, 전달·처리·완료의 증거가 아닙니다.

- `available`: 살아 있는 relay가 깨울 수 있거나, 이미 울린 깨우기가 다시 울릴 시각을 기다리고 있습니다.
- `degraded`: 이 세션의 깨우기가 계속 실패하거나 필요한 조건이 빠졌습니다. 큐의 메시지는 받는 세션의 다음 경계(턴 종료, 도구 경계, 입력)에서만 전달됩니다.
- `unsupported`: 받는 세션이 선언한 기능에 쉬는 동안의 깨우기가 없습니다.
- `no-live-relay`: 온라인 presence나 relay lease가 없어 깨울 수 없습니다. 예를 들어 재부팅 뒤 아직 턴이 없는 세션입니다. 메시지는 큐에 남습니다.

Esc로 중단된 Codex 세션은 사용자가 재개할 때까지 깨울 수 없습니다.

### Codex queue wake 설정

Codex는 기본적으로 `codex-deferred`를 씁니다. 대기열 깨우기를 쓰려면 Codex 플러그인 hook 환경이 알려 준 절대 `PLUGIN_DATA` 폴더 아래 `session-messaging.json`을 다음과 같이 둡니다. 설치 캐시 안의 파일이나 공유 메시지 DB가 아니라 플러그인 데이터 파일입니다. 이 설정은 다른 호스트의 깨우기 방식을 바꾸지 않습니다.

```json
{"schemaVersion":"1.0.0","codex":{"queueWake":true}}
```

- 환경 변수 `AGENT_GOVERNANCE_CODEX_QUEUE_WAKE`가 파일보다 우선합니다. 정확히 `1`이면 켜고 `0`이면 파일이 `true`여도 끕니다. 다른 값은 진단 후 끕니다.
- 환경 변수가 없을 때만 파일을 읽으며 `codex.queueWake`는 boolean이어야 합니다. `false`, 파일 없음, `PLUGIN_DATA` 없음은 기본 지연을 유지합니다.
- 상대 경로, 잘못된 JSON·UTF-8·schema·타입, 일반 파일이 아닌 대상, 4096바이트 초과, 읽기 오류는 켜지 않고 제한된 진단만 stderr에 남깁니다. 경로·본문·비밀을 진단에 넣지 않으며 다른 위치에서 대신 찾지 않습니다.
- 설정을 바꾼 뒤에는 받는 세션의 새 `SessionStart`(시작·재개·clear·compact)가 필요합니다. 기존 relay는 시작할 때 받은 방식을 유지하므로, 설정 파일만 쓰거나 MCP 서버만 다시 시작한 상태를 전환 완료로 보지 않습니다.
- queue wake는 화면에 보이는 사용자 메시지로 들어가며 조용한 깨우기가 아닙니다. 설정만으로 실제 깨우기·본문 수신·ACK가 확인된 것은 아닙니다.

## 두 세션으로 확인해 보기

같은 프로젝트를 연 세션 두 개에 다음처럼 요청합니다. 코드는 바꾸지 않습니다.

```text
[검토 세션]
AGS 현황판의 현재 작업을 "AGS-DEMO-REVIEW · 테스트 실행 방법 검토"로 기록해 줘.
PEER 메시지로 검토 요청이 오면 전달받은 파일을 직접 읽고 설명이 맞는지 확인해,
ACK를 남기고 결과와 근거를 별도 PEER 메시지로 회신해 줘. 파일 수정과 테스트 실행은 하지 마.

[조사 세션]
이 프로젝트의 테스트 실행 방법을 문서와 설정에서 찾아 명령과 근거 파일 위치를 정리해 줘.
현황판에서 "AGS-DEMO-REVIEW"를 맡은 세션을 찾아 PEER 메시지로 검토를 요청하고,
ACK와 실제 검토 결과를 구분해서 알려 줘. 파일 수정과 테스트 실행은 하지 마.
```

## 로컬 프로세스

AGS 메시징은 공유 SQLite 파일을 각 프로세스가 직접 엽니다. 별도 메시지 broker 서버, TCP 수신 포트, broker 인증서나 token은 없습니다. 다만 세션의 생존 확인과 깨우기를 맡는 **relay 프로세스는 실행될 수 있습니다.** relay는 세션 시작 hook에서 뜨고 호스트 프로세스와 lease에 묶여 동작합니다. 호스트 자체나 외부 모델 서비스의 네트워크 사용은 이 메시징 구조와 별개입니다.

## 한계

- 같은 OS 사용자 권한의 프로그램은 상태 폴더의 DB를 읽거나 바꿀 수 있습니다. 세션 식별자는 인증된 사용자가 아닙니다.
- PEER 메시지는 승인·권한·외부 변경 의사를 대신하지 않습니다.
- 받는 모델이 메시지 업무를 정확히 한 번 실행한다는 보장은 없습니다.
