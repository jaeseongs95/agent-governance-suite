# v2.7.7: 세션 메시지 한글 조각 경계 수정

세션 메시지의 broker 응답과 요청을 받는 쪽이 여러 byte로 된 문자를 깨뜨리던 결함을 고칩니다. client의 응답 reader와 broker의 요청 reader는 TLS에서 받은 조각마다 UTF-8 문자열로 바꿔 이어 붙였습니다. Node TLS는 평문을 16384 byte 이하의 조각으로 넘기므로, 한글(3 byte)이나 이모지(4 byte)가 조각 경계에 걸리면 그 문자가 U+FFFD로 바뀌었습니다. 크기도 바꾼 문자열로 다시 셌으므로, 깨진 문자만큼 byte 수가 늘었습니다.

피해는 hook 없는 CLI claim 경로에서 났습니다. 이 경로는 기본값(최대 10개, 응답 32 KiB)으로 받으므로 응답이 16384 byte를 넘을 수 있습니다. 한글 메시지 8개씩 12묶음을 claim하는 시험에서 11묶음이 깨졌습니다. 메시지 ID는 ASCII라서 ACK가 성공하므로, 깨진 본문은 그대로 소비됐습니다. 응답이 한도에 가까우면 다른 결과가 났습니다. broker가 한도 안으로 맞춘 응답을 client가 한도 초과로 거절하고 조용히 한 번 더 요청했습니다. 그 사이 첫 요청이 메시지에 lease를 걸었으므로 두 번째 요청은 0개를 받았습니다. 한글 메시지 9개로 32767 byte 응답을 만든 시험에서 CLI는 0개를 반환했고, 9행이 첫 lease(120초) 동안 묶였습니다. hook 전달 경로는 한 번에 한 메시지(본문 4096 byte 이하)만 받으므로, 일반 텍스트 본문이면 응답이 16384 byte에 닿지 않습니다. 다만 제어 문자는 JSON에서 `\u0001`처럼 6 byte로 늘어나므로, 제어 문자가 많은 본문은 hook 경로에서도 응답이 16384 byte를 넘어 같은 결함을 겪을 수 있었습니다. 이번 수정은 이 경우도 고칩니다.

이제 client와 broker가 같은 줄 reader 하나를 씁니다. reader는 받은 조각을 byte 그대로 모으고, 줄바꿈(0x0A)을 byte에서 찾습니다. 줄이 완성되면 그 줄만 한 번 UTF-8로 풉니다. 한도는 byte 수로 셉니다. 줄바꿈을 포함한 줄이 32768 byte 이하이면 받고, 그보다 크면 전과 같은 오류로 거절합니다. client의 오류는 "The broker response exceeded its limit.", broker의 오류는 "Request exceeds the broker limit."입니다. broker가 응답을 한도 안으로 맞출 때 세는 방식(줄바꿈을 포함한 UTF-8 byte)과 한 byte까지 같습니다. protocol `1.0.0`, 요청·응답 한도 32 KiB, 거절과 일반 오류의 구분, 현황판 presence 조회, 출력 계약과 schema는 바뀌지 않았습니다.

## 동작 변화(호환성)

ASCII만 담긴 메시지나 16384 byte보다 짧은 응답에서는 결과가 전과 같습니다. 달라지는 경우는 여러 byte로 된 문자가 조각 경계에 걸릴 때뿐입니다. 이제 원문 그대로 받고, 크기가 한도 안이면 거절하지 않습니다.

응답은 broker가 만든 byte를 client가 읽으므로, 2.7.7 client는 이전 broker의 응답도 깨지지 않게 받습니다. 요청은 broker가 읽으므로 이전 broker의 reader가 그대로 적용됩니다. 번들 client가 보내는 요청은 본문이 4096 byte 이하라 일반 텍스트 본문이면 16384 byte에 닿지 않습니다. 제어 문자가 많아 JSON escape로 크게 늘어나는 본문은 요청도 16384 byte를 넘을 수 있고, 이때는 이전 broker의 reader가 그대로 적용됩니다. previous-broker 회귀 시험은 v2.7.6, v2.7.5, v2.7.3 broker로 통과했습니다. 이 시험에서 새 client는 이전 broker가 보낸 32768 byte 한글 응답을 온전히 받았고, 같은 크기의 한글 요청은 이전 broker가 전처럼 한도 초과로 거절했습니다. 이 검사로 혼합 버전의 모든 실행·복구를 보장하지 않습니다.

## 알려진 한계

2.7.6 이하 client는 업그레이드하기 전까지 이 결함이 그대로 남습니다. 이전 broker의 요청 reader도 broker를 2.7.7로 바꾸기 전까지 그대로입니다. 이미 깨진 채 ACK된 메시지는 원문이 남아 있지 않으므로 되돌릴 수 없습니다.

조각 경계와 한도는 Linux 환경의 시험(reader 단위 시험, 실제 broker와 TLS로 주고받는 경계 시험, CLI claim 경로의 한글 묶음 시험)으로 확인했습니다. Windows와 실제 PC의 동작은 이 검사가 대신하지 않습니다. 공통 접수 원문이 두 번 주입되는 문제(L3)와 presence 조회 보충(`list-presence-fill`)은 이번 범위가 아닙니다.

공식 [설치 안내](../README.md#설치)에 따라 업데이트한 뒤 새 세션으로 재연결합니다. 운영 DB·키·큐를 지우거나 덮어써 불확실한 상태를 없애지 않습니다. 버전 동기화와 로컬 검사는 실제 설치 bytes나 호스트 동작을 대신하지 않으므로, 설치·재연결 뒤 한글 메시지 전달을 별도로 확인합니다.
