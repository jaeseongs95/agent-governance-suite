# v2.7.6: 현황판 presence 조회 대기 상한

세션 현황판(`list_session_status`)의 presence 조회 전체에 대기 상한을 둡니다. 2.7.4부터 서버는 현황판 세션을 3개씩 묶어 broker에 순서대로 물었고, 묶음 하나에는 client deadline(20초)이 있었지만 조회 전체에는 상한이 없었습니다. broker가 아예 답하지 않으면 첫 묶음 뒤에 멈췄지만, 답은 하되 묶음마다 느리면 대기가 묶음 수만큼 늘었습니다. 요청 하나의 한도 안에서 묶음마다 1.9초가 걸리면 300개 세션(100개 묶음)에서 190초입니다. 시험으로 재현했습니다. 묶음마다 1초씩 답을 늦추는 실제 broker에서 90개 세션 조회가 약 30초 걸렸습니다.

이제 조회 전체가 client deadline 하나(20초)를 나눠 씁니다. 묶음마다 남은 시간만 client에 넘기고, 남은 시간이 없으면 더 묻지 않습니다. deadline에 걸린 묶음은 client가 연결을 끊습니다. 그 묶음과 남은 묶음의 세션은 broker가 답하지 않은 것으로 보고 `unknown`(`autoWake: null`)으로 두며, 앞서 받은 결과는 그대로 보여 줍니다. 끊은 요청의 응답이 뒤늦게 와도 결과는 바뀌지 않습니다. 같은 실제 broker에서 조회는 약 20초에 끝났습니다. 거절된 묶음만 `unknown`으로 두는 규칙, 거절이 아닌 실패에서 멈추는 규칙, broker가 받지 않는 형식의 세션을 묻지 않는 규칙, 묶음 크기 3과 응답 한도는 그대로입니다. 자세한 규칙은 [presence 보존과 현황판 조회](session-message-lifecycle.md#presence-보존과-현황판-조회)를 따릅니다.

20초는 다른 broker 요청 하나의 client deadline과 같은 값입니다. broker가 떠 있지 않아 새로 띄우는 첫 조회(기동 대기 최대 15초)도 이 안에서 끝날 수 있고, 호스트의 MCP 도구 호출 제한(Codex 기본 60초)보다 짧습니다. 새 설정은 없습니다. 묶음을 동시에 보내는 방식은 택하지 않았습니다. broker는 요청을 한 process에서 차례로 처리하므로 동시에 보내도 broker 쪽 처리 시간은 줄지 않고, 순서·중복·실패 처리만 복잡해집니다. 정상 broker에서 300개 세션 조회는 약 0.5초입니다.

## 동작 변화(호환성)

정상 broker에서는 결과와 시간이 전과 같습니다. 달라지는 경우는 조회가 20초를 넘길 때뿐입니다. 전에는 끝까지 기다렸지만, 이제 20초에 멈추고 받지 못한 세션을 `unknown`으로 보여 줍니다. 다시 조회하면 다시 묻습니다.

이 변경은 서버(client) 쪽에만 있습니다. broker 계약과 schema는 바뀌지 않았으므로, 2.7.6 서버는 2.7.5·2.7.4 broker와도 같은 상한으로 동작합니다. previous-broker 회귀 시험은 v2.7.5, v2.7.4 broker로 통과했으며, 이 검사로 혼합 버전의 모든 실행·복구를 보장하지 않습니다. 2.7.4보다 이전 broker는 요청한 세션 목록을 무시하므로 2.7.4 notes의 혼합 버전 표를 따릅니다.

presence 보존 시험(342 identity, 1302행 DB)이 느린 Windows runner에서 시간 초과로 실패하던 문제도 고쳤습니다. 원인은 현황판 조회가 아니라 시험 fixture였습니다. fixture가 행을 약 2000번의 개별 commit으로 쓰고 있었고, 그 조회는 44개 세션(15개 묶음)뿐이었습니다. fixture를 transaction 하나로 묶었고, 제품 동작과 시험 한도는 바꾸지 않았습니다. fsync마다 20ms를 더한 흉내에서 두 시험은 48.6초와 47.3초에서 1.7초와 2.5초로 줄었습니다.

## 알려진 한계

broker가 20초 안에 다 답하지 못할 만큼 느리면, 현황판의 뒤쪽 세션은 그 조회에서 `unknown`으로 보입니다. 어느 세션이 뒤쪽인지는 현황판 순서를 따릅니다.

대기 상한은 presence 조회에만 둡니다. 현황판 파일을 읽는 시간과 다른 broker 요청의 deadline은 그대로입니다. 공통 접수 원문이 두 번 주입되는 문제(L3)는 이번 범위가 아닙니다.

상한과 시험 시간은 Linux 환경의 시험(가짜 client와 느린 실제 broker)으로 확인했습니다. 실제 PC와 Windows runner의 동작은 이 검사가 대신하지 않습니다.

공식 [설치 안내](../README.md#설치)에 따라 업데이트한 뒤 새 세션으로 재연결합니다. 운영 DB·키·큐를 지우거나 덮어써 불확실한 상태를 없애지 않습니다. 버전 동기화와 로컬 검사는 실제 설치 bytes나 호스트 동작을 대신하지 않으므로, 설치·재연결 뒤 현황판 presence를 별도로 확인합니다.
