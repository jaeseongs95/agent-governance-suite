# 소프트웨어 설계

모듈 `software-design` · v0.1.0 · 상태 `draft`



추가 분야로 작성한 규칙이다. 명시적 도입 근거를 기록한 작업에서 사용하고 적용성을 직접 확인한다.



## DESIGN-CONTRACT-001 — 모듈 경계와 책임

**원리:** 입력·출력·권한·소유권을 하나의 책임에 맞춘다.

**불변조건:** 전문 모듈이 기존 조정·감사·승인 책임을 몰래 대신하지 않는다.

**적용 조건:** 새 모듈·서비스·스킬을 추가한다.

**가정:** 요청과 허용된 대상의 실제 코드·운영 경계가 확인되어 있다.

**실패 형태:** CS 스킬이 자체 세션·DB·배포 승인을 만들어 기존 경로를 우회한다.

**판단 질문:** 기존 책임과 중복되는가? / 외부 부작용과 오류 계약은 명시됐는가?

**검증 의무:** 공개 입력·출력과 호출 경로를 검토하고 금지된 부작용이 없는지 확인한다.

**하지 않을 일:** 추상화 자체를 목적 삼아 모든 로직을 계층화하지 않는다.

**출처 식별자:** AGS-DESIGN (`assets/sources.json`에서 범위와 원문 위치를 확인한다.)



## DESIGN-STATE-002 — 명시적 상태 전이

**원리:** 가능한 전이를 정의하고 불가능한 전이를 거부한다.

**불변조건:** 완료·검증·미실행 상태가 혼동되지 않는다.

**적용 조건:** 진행·실패·재시도·완료 상태를 저장한다.

**가정:** 요청과 허용된 대상의 실제 코드·운영 경계가 확인되어 있다.

**실패 형태:** NOT_RUN 결과가 empty findings 때문에 PASS로 바뀐다.

**판단 질문:** 최종 상태에서 재개가 가능한 조건은 무엇인가? / 중복 이벤트는 어떻게 처리하는가?

**검증 의무:** 전이 표의 허용·거부 간선을 모두 검사하고 replay·stale 상태를 추가한다.

**하지 않을 일:** 불필요한 상태를 늘려 읽기 어렵게 만들지 않는다.

**출처 식별자:** AGS-DESIGN (`assets/sources.json`에서 범위와 원문 위치를 확인한다.)



## DESIGN-COMPAT-003 — 계약 버전과 호환성

**원리:** 허용 필드·버전·의미 변경을 명시적으로 분기한다.

**불변조건:** 구버전 경로가 새 필수 조건을 조용히 제거하거나 우회하지 않는다.

**적용 조건:** 입출력·저장 schema를 확장한다.

**가정:** 요청과 허용된 대상의 실제 코드·운영 경계가 확인되어 있다.

**실패 형태:** 알 수 없는 필드를 버리고 요청을 구버전 형식으로 재시도한다.

**판단 질문:** 추가 필드가 서명·digest·재개에 보존되는가? / 기존 데이터 읽기는 가능한가?

**검증 의무:** 구·신 버전 교차 입력과 필드 손실·stale revision·downgrade를 시험한다.

**하지 않을 일:** 모든 계약의 버전을 한꺼번에 올리지 않는다.

**출처 식별자:** AGS-DESIGN (`assets/sources.json`에서 범위와 원문 위치를 확인한다.)



## DESIGN-MINIMAL-004 — 불변조건을 만족하는 최소 변경

**원리:** 필수 정확성·권한·검증을 보존한 채 복잡도를 최소화한다.

**불변조건:** 불필요한 서비스·의존성 없이 동결된 요구를 충족한다.

**적용 조건:** 여러 구현 대안 중 선택한다.

**가정:** 요청과 허용된 대상의 실제 코드·운영 경계가 확인되어 있다.

**실패 형태:** 단순함을 이유로 재시도 정합성·감사·검증을 삭제한다.

**판단 질문:** 기존 기능으로 해결할 수 있는가? / 대안별 실패 범위와 운영 비용은 무엇인가?

**검증 의무:** 필수 조건과 변경 범위를 대조하고 미채택 대안의 실제 필요성을 검토한다.

**하지 않을 일:** 권고를 gate로 승격해 사용자 범위를 확대하지 않는다.

**출처 식별자:** AGS-DESIGN (`assets/sources.json`에서 범위와 원문 위치를 확인한다.)
