# debugging

이 모듈이 필요한 작업에서만 읽는다. 기존 AGS 권한·역할·계약을 유지한다. 규칙 원본은 [catalog.json](catalog.json)이며 모델 행동 평가는 NOT_RUN이다.

## DBG-001 — 사실과 원인 가설 분리

**담당:** blocker-diagnostician

**적용:** 실패 진단 시작

**행동:** 기대 결과·실제 결과·재현 조건을 먼저 기록하고 각각의 원인 가설에 지지 관측을 붙인다.

**근거:** 오류 원문 위치, 입력과 실행 환경을 보존한다.

**피할 실패:** 실패 메시지를 읽지 않고 라이브러리 교체부터 하지 않는다.

**예외:** 현존 근거가 하나의 원인을 강하게 지지하면 그 수준으로 결론을 낸다.

출처: SP-DEBUG ([고정 커밋](sources.lock.json)).

## DBG-002 — 차이를 좁히는 비교

**담당:** blocker-diagnostician

**적용:** 정상 환경과 실패 환경이 있을 때

**행동:** 정상 경로와 실패 경로의 입력·설정·버전·권한 차이에서 원인을 구별할 최소 검사를 선택한다.

**근거:** 변경한 변수와 기대 판별 결과를 남긴다.

**피할 실패:** 여러 설정을 동시에 바꾸고 무엇이 해결했는지 모르게 하지 않는다.

**예외:** 독립적으로 확인된 별도 결함은 별개 작업으로 분리할 수 있다.

출처: SP-DEBUG ([고정 커밋](sources.lock.json)).

## DBG-003 — 경계에서 데이터 추적

**담당:** blocker-diagnostician

**적용:** 여러 프로세스·도구가 연결된 실패

**행동:** 데이터·설정이 어느 경계에서 바뀌거나 사라지는지 관찰하고 최초 불일치를 좁힌다.

**근거:** 요청 ID·버전·허용된 메타데이터를 이용한 입출력 기록을 남긴다.

**피할 실패:** 환경 변수 전체 덤프나 비밀 본문 로그를 진단 수단으로 사용하지 않는다.

**예외:** 민감 정보는 존재 여부·형식·redacted value 등 최소 정보만 기록한다.

출처: SP-DEBUG ([고정 커밋](sources.lock.json)).

## DBG-004 — 기존 시도의 정보량 확인

**담당:** blocker-diagnostician

**적용:** 같은 수정이 반복 실패

**행동:** 직전 가설과 검사 결과를 읽고 다음 시도가 어떤 새 정보를 얻는지 명시한다.

**근거:** 반증한 가설과 미해결 가설, 다음 판별 검사를 남긴다.

**피할 실패:** 실패 횟수만으로 구조적 결함이라고 단정하지 않는다.

**예외:** 반복 예산·중단·재계약은 기존 iteration-frame-auditor의 결정을 따른다.

출처: SP-DEBUG ([고정 커밋](sources.lock.json)).

## DBG-005 — 복구와 근본 수정 구분

**담당:** blocker-diagnostician

**적용:** 장애를 빨리 줄여야 할 때

**행동:** 기존 승인 범위의 containment를 원인 해결과 구분하고 후속 재현·원인 확인을 연결한다.

**근거:** 복구 범위·남은 위험·되돌리기 조건을 기록한다.

**피할 실패:** 원인 100% 확정 전에는 아무 복구도 할 수 없다는 규칙을 만들지 않는다.

**예외:** 데이터 삭제·권한 확대·배포 등은 기존 사전 점검과 승인 조건을 그대로 따른다.

출처: SP-DEBUG ([고정 커밋](sources.lock.json)).

## DBG-006 — 원래 증상으로 종료 확인

**담당:** blocker-diagnostician

**적용:** 수정 후

**행동:** 최초 재현 경로와 관련 회귀를 다시 실행하고 필요한 환경까지 범위를 구분한다.

**근거:** 수정 후보와 원래 증상 검사의 실행 근거를 acceptance 담당에게 전달한다.

**피할 실패:** 관련 없는 테스트 통과만으로 장애가 해결됐다고 하지 않는다.

**예외:** 환경이 없으면 검증되지 않은 범위를 남긴다.

출처: SP-DEBUG ([고정 커밋](sources.lock.json)).
