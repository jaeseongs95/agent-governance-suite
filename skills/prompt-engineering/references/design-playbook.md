# 프롬프트 설계 기준

## 1. 고칠 대상을 분리

| 관찰 | 우선 확인 | 결과 |
| --- | --- | --- |
| 다른 대상을 수정하거나 범위를 넓힘 | 원문·최근 정정·출력/작업 단위 | 대상과 완료 조건을 구체화 |
| 지침을 읽고도 반대로 실행 | 충돌하는 문장, 적용 계층, 실제 도구 계약 | 충돌 위치와 최소 변경 제시 |
| JSON 형식만 맞고 사실이 틀림 | 입력 근거, 추출 규칙, 누락 처리 | 구조와 내용 평가 분리 |
| 403·timeout·파일 없음 | 실제 요청·응답·경로·권한 | 환경 문제로 기록, 문구 강화로 덮지 않음 |
| 대량 입력을 한 줄씩 읽고 저장 | 도구의 범위 읽기·배치 지원, 사용자 파일 단위 | 의미를 보존하는 묶음 처리와 최종 산출물 단위 명시 |
| 긴 세션에서 옛 판단 반복 | 정정 출처, 폐기한 해석, 현재 유효 기준 | 최신 기준을 실행 가능한 조건으로 반영 |

여러 근거가 같은 설명을 강하게 지지하면 그 수준으로 결론을 적어라. 확인하지 못한 내부 동기와 관찰로 확인한 실질적 결과를 구분하라.

## 2. 최소 구성

1. **목표:** 무엇이 나오면 완료인지 한두 문장으로 적어라.
2. **맥락:** 판단에 필요한 사실·원문·파일·실패 사례와 출처만 포함하라.
3. **범위:** 대상·제외·기존 승인·변경 금지를 원문 의미대로 보존하라.
4. **행동:** 중요한 판단 순서와 필요한 도구 조건을 명시하라. 이미 승인된 후속 작업은 계속하게 하라.
5. **출력:** 사람용 문장인지 기계용 schema인지 구분하고 필수 내용·누락·실패 상태를 정하라.
6. **검증:** 실제 확인할 동작과 남길 증거를 지정하라. 산출물 존재만으로 완료라고 하지 마라.

단순 요청이면 필요한 항목만 남겨라. 역할극·반복 경고·칭찬·처벌 표현을 구체적인 행동 조건으로 바꿔라. 역할 정의를 실제 목표보다 상위에 놓지 마라.

## 3. 기법을 고르는 기준

| 문제 | 선택할 기법 | 확인할 부작용 |
| --- | --- | --- |
| 작업 경계가 흐림 | 목표·금지·완료 조건 명시 | 요청하지 않은 제한·재승인 추가 |
| 업무 텍스트와 지시가 섞임 | 메시지 역할·입력 구획·출처 표시 | 구분자를 보안 통제라고 오해 |
| 출력 형식 반복 오류 | 확인된 structured output 지원 또는 간결한 schema·파서 | 형식 성공을 사실 성공으로 오해 |
| 특정 경계에서 오분류 | 실제 실패와 다른 입력의 소수 예시 | 평가 정답 누출·예시 편향 |
| 복잡한 작업에서 누락 | 명확한 하위 결과와 체크포인트 | 불필요한 에이전트·파일·호출 폭증 |
| 긴 맥락에서 정보 누락 | 필요한 근거 묶음·출처·정정 우선 정리 | 조건·부정·불확실성 삭제 |
| 설명이 과도함 | 필요한 결론·짧은 근거·증거 형식 | 필수 판단·누락사항까지 제거 |

예시 개수, XML 사용, 영어 전환, chain, agent 수를 전역 정답으로 고정하지 마라. 현재 실패를 해결하는 최소 기법을 비교하라. 내부 사고 과정 대신 검토 가능한 결과와 짧은 근거를 요청하라.

## 4. 실행 환경과 비용

- OS·셸·파일 경로·실제 도구 목록을 확인하라. 다른 제품에만 있는 기능을 공통 프롬프트에 넣지 마라.
- 안정된 지시와 가변 데이터를 분리하되 실제 호스트의 메시지 역할·캐시·컨텍스트 규칙을 먼저 확인하라. 구조 변경만으로 캐시 hit·토큰 절감률을 예측하지 마라.
- 대량 입력은 도구의 적정 범위로 묶고, 개별 결과가 필요한 경우 내부 항목 ID를 유지하라. 사용자 요청이 개별 파일이면 그 단위를 보존하라.
- 호출 수·토큰·시간 상한은 기존 합의에서 가져와라. 새 유료 API·보조 모델·무한 재시도를 숨겨 넣지 마라.
- 프롬프트를 줄일 때 부정·예외·권한·복구·출력 조건을 삭제하지 마라.

## 5. 요구 추적 예

원 요청: “Windows에서 이미 읽기 권한을 받은 로그를 분석하고 보고서 하나를 저장해. 소스는 수정하지 마.”

보존할 조건은 Windows 환경, 기존 읽기 승인, 로그 분석, 보고서 한 개, 소스 변경 금지다. 초안은 이 다섯 조건을 실제 행동과 연결해야 한다. “역할상 파일을 못 읽는다”, “파일마다 보고서를 만든다”, “먼저 Linux 명령을 설치한다”, “분석하면서 소스를 고친다”는 요구 손실이다.
