# 원칙별 판단 기준

설계 원칙은 실제 변경 비용과 계약을 판단하는 도구다. 구조·파일 수·패턴 이름 자체를 품질 점수로 쓰지 마라. 원칙의 일반 정의와 아래 AGS 적용 판단을 구분하라.

## SRP — 하나의 변경 책임

현재 모듈을 바꾸게 하는 요구 주체·정책·운영 경계를 찾아라. 같은 기능의 연속 단계라는 이유만으로 서로 다른 정책 변경을 묶지 말고, 코드가 길다는 이유만으로 하나의 응집된 책임을 잘게 나누지 마라.

예를 들어 승인 정책과 특정 호스트의 메시지 인코딩이 같은 함수에 있으면 각 변경이 다른 기능을 깨뜨리는지 호출 경로로 확인하라. 실제로 독립된 변경 이유가 있으면 기존 policy와 adapter 경계를 사용하라. 관련 도우미까지 전부 새 서비스로 만들 필요는 없다.

## OCP — 확인된 변화에 대한 확장

이번 요구의 변화 축과 기존 확장 지점을 먼저 찾아라. 호스트 추가마다 공용 정책 곳곳에 제품명을 분기한다면 해당 축을 기존 adapter/registry 경계에 모으는 대안을 검토하라.

기존 소스 수정 자체는 위반이 아니다. 버그·잘못된 계약·새로 확인된 요구 때문에 기존 코드를 고칠 수 있다. 한 곳에 모인 명시적 dispatch·allowlist·보안 정책표는 그 목적을 확인하고 유지할 수 있다. 아직 없는 두 번째 소비자를 위해 전 범용 plugin framework를 만들지 마라.

## LSP — 소비자 관점의 의미 보존

상속 선언 유무보다 같은 계약으로 대체되는 함수·provider·adapter의 관찰 가능한 동작을 확인하라. 공통 타입과 컴파일 성공은 필요할 수 있지만 충분하지 않다.

- 계약상 허용 입력에 새 사전조건을 몰래 붙이지 않는가?
- 성공 보장과 오류 구분을 약화하지 않는가? 권한 거부·일시 실패를 성공 또는 빈 결과로 바꾸지 않는가?
- 부작용·취소·해제·재시도·중복 처리가 소비자 계약과 일치하는가?
- 공유 상태의 불변조건과 허용된 상태 변화 이력이 유지되는가?
- 순서·시간·일관성은 해당 계약이 보장하는 수준만 요구하는가?

서로 다른 능력 자체가 위반은 아니다. 실제 capability를 좁게 선언하고 소비자가 지원 여부를 확인하는 계약이면 그 범위에서 판단하라. 지원하지 않는 기능을 공통 계약으로 광고한 뒤 성공으로 무시하거나 예고 없이 예외를 내는 경로를 구분하라. 검증 질문은 기존 테스트 담당에 전달하라.

## ISP — 소비자가 필요한 계약

구현자가 얼마나 많은 메서드를 갖는지보다 소비자가 무엇을 알아야 하는지 살펴라. 읽기 전용 소비자에게 쓰기·관리 권한이나 vendor SDK를 요구한다면 사용 중인 능력으로 경계를 좁혀라.

함수 타입, TypeScript의 좁은 structural type, 기존 capability view처럼 작은 수단을 우선하라. 외부 공개 계약을 깨는 분리는 호환성·버전·이행 계획을 먼저 확인하라. 일관된 자원 수명 단위를 억지로 쪼개지는 마라.

## DIP — 정책과 세부 구현의 의존 방향

정책 코드가 특정 SDK·OS·DB·전송 형식에 직접 묶여 정책 변경과 배포가 함께 흔들리는지 확인하라. 정책이 필요한 좁은 동작을 계약으로 두고, 세부 adapter가 그 계약에 맞추도록 하라. 실제 구현 선택은 기존 조립 지점에서 처리하라.

의존성 주입은 수단이며 DIP의 판정 기준 자체가 아니다. 이미 전달받는 함수나 객체로 충분하면 DI 프레임워크·abstract base class·factory를 추가하지 마라. 안정된 언어 기본 기능이나 stdlib 사용을 일괄 추상화하지 마라.

구현이 하나뿐이어도 vendor, 권한, 전송, 자원 수명의 경계는 필요할 수 있다. 반대로 구현이 여러 개라는 사실만으로 유용한 추상화가 입증되는 것도 아니다. 소비자에게 보장할 계약과 격리할 변화가 무엇인지 근거로 결정하라.
