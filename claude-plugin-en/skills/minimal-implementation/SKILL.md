# Minimal Complete Work

이 스킬을 적용할 때 [공통 행동 기준](../independent-audit-gate/references/specialist-behavior.md)을 먼저 읽고 따른다.

요구를 모두 충족하는 가장 작은 완전한 결과를 만든다. 결과물의 종류(코드, 문서, 데이터, 설정, 절차, 디자인)는 가리지 않는다. 작게 만든다는 것은 필요 없는 것을 더하지 않는다는 뜻이며 요구·정확성·검증을 줄인다는 뜻이 아니다.

## 먼저 이해한다

- 요청 목적과 수용 기준, 결과물이 실제로 쓰이는 경로(호출자·독자·실행 환경)를 끝까지 읽는다. 아래 단계는 이해한 뒤에 고른다.
- 결함 수정은 증상이 아니라 깨진 불변조건이 있는 자리에서 고친다. 같은 원인을 공유하는 다른 경로도 확인하고, 이미 올바르게 동작하는 호출자는 보존한다. 원본을 그대로 따라 적어야 하는 손 목록(예: 복사할 파일, import, 경로)은 원본에서 도출하거나 빠지면 실패하는 검사를 둔다. 의도된 허용 목록과 시험 사례 표는 손으로 둔다.

## 단계

요구·불변조건·실제 대상 환경을 처음으로 만족하는 단계에서 멈춘다.

1. **꼭 있어야 하나?** 추측성 추가는 하지 않는다. 명시된 요구는 추측이 아니며, 빼려면 범위 변경으로 제안한다.
2. **이미 있나?** 저장소·문서·자료에 있는 함수·양식·절차·데이터를 다시 쓴다.
3. **표준이 하나?** 그 분야의 표준(예: 표준 라이브러리, 표준 양식, 기존 관례).
4. **플랫폼 기능이 하나?** DB 제약, 네이티브 입력, 도구 내장 기능 같은 것.
5. **이미 설치된 도구·의존성이 하나?** 몇 줄로 될 일에 새 의존성을 더하지 않는다.
6. **한 줄로 분명히 되나?** 오류 처리·소유권·동작이 드러날 때만.
7. **그다음에야** 최소 완전 결과물.

같은 크기의 두 방법이면 경계 사례에서 올바른 쪽을 고른다. 라이브러리·플랫폼 기능으로 대체하기 전에 의미, 지원 플랫폼, 동시성, 자원 수명이 같은지 확인한다. 짧은 정상 경로 시연은 충분한 근거가 아니다.

## 대체물로 완료를 만들지 않는다

- 모의 객체·시뮬레이터, 고정 결과·하드코딩 값, 자리 채움 내용, 실패할 때 조용히 끼어드는 대체 경로(폴백·더미 생성), 삼키거나 성공 상태로 덮은 오류는 실제 경로가 아니다. 이런 것이 낸 통과·출력은 완료 근거로 세지 않는다.
- 시험·시연·격리에 대체물이 필요하면 드러나게 둔다. 기본값은 꺼짐으로 하고, 이름이나 표시로 구분하고, 실제 경로에서 쓰이지 않는지 확인한다.
- 대체물이나 아직 만들지 않은 경로가 남아 있으면 「완료」로 보고하지 않고 위치(파일·줄·항목), 이유, 실제 경로로 바꿀 조건을 적는다.
- 오류를 삼키거나 다른 원인·성공 상태로 바꾸지 않는다. 호출자와 독자가 무엇이 실패했는지 알 수 있게 한다.

## 규칙

- 추측성 추상화·뼈대를 만들지 않는다. 현재 호출자, 변화 축, 계약 경계가 있을 때만 둔다. 벤더·호스트 어댑터는 하나뿐이어도 프로토콜·권한·전송·자원 수명을 가르면 유지한다.
- 동작과 필요한 근거가 남으면 삭제를 우선한다. 영리한 압축보다 읽기 쉬운 쪽을 고른다.
- 줄일 대상은 영향받는 호출자와 검증을 포함한 변경 전체다. 파일 수와 변경 분량은 수용 기준이 아니다.
- 복잡한 요청도 요구된 동작을 가장 작은 적합한 설계로 끝까지 만든다. 축소판을 내고 원래 요구를 원하느냐고 되묻지 않는다. 일상적인 선택은 직접 정한다.
- 알려진 한계가 있는 의도적 단순화(전역 잠금, O(n²) 탐색, 단순 규칙)는 `ceiling:` 주석이나 표시로 한계와 확장 경로를 남긴다. 예: `// ceiling: 전역 잠금, 처리량이 문제면 계정별 잠금`.
- 실제 측정값을 다루는 물리·운영 대상에는 보정할 설정값을 남긴다.

## 줄이지 않는 것

신뢰 경계의 입력 검증, 데이터 손실을 막거나 무엇이 실패했는지 알리는 오류 처리, 보안 조치, 접근성 기본, 명시적으로 요청된 것은 줄이지 않는다. 사용자가 전체판을 원하면 다시 따지지 않고 만든다. 문제를 이해하는 데 드는 읽기는 줄이지 않는다.

## 검증

- 필요한 검증이 빠진 결과는 끝나지 않은 것이다. 작업 공간의 기존 시험 도구·관례·위치를 쓰고, 기존 범위로 결함을 잡을 수 없을 때만 집중 회귀 시험을 더한다. 되돌리기 쉬운 사소한 변경에 시험을 꾸며 내지 않는다.
- 결함 수정은 원래 실패 조건을 지정된 환경에서 실행해 확인한다. 재현할 수 있으면 수정 전 실패를 보이고, 없으면 그 공백을 적는다.
- 운영 작업(파일 이동, 장부 반영, 설정 변경, 요청된 이전)도 같은 단계를 따른다. 허용된 환경의 기존 도구로 하고 결과를 개수·해시·조회·기존 시험으로 직접 확인한다. 사용자 제약이나 실제 간섭 위험이 있을 때만 격리 사본이나 fixture를 만든다. 영구 삭제·운영 데이터·배포·권한·비밀·결제 같은 고위험 관문은 그대로 두고, 승인이 없으면 대상·영향·정확한 명령을 담아 한 번 묻는다.

## 출력

결과물, 실제로 한 검증, 중요한 남은 한계(남은 대체물 포함)를 적는다. 일상적인 설명은 짧게 하되 실패 근거와 중요한 절충은 지우지 않는다. 보고서나 단계별 설명을 요청받으면 그대로 다 쓴다.

형식: `[결과] → 검증: [근거] → 남은 것: [있을 때만]`.

워크플로 단계 결과는 `output.status`로 `passed`, `failed`, `blocked` 중 하나를 적는다. 실제 실행이 실패했으면 `failed`와 `GATE_FAILED` 오류로, 필요한 근거나 입력이 없으면 `blocked`로 기록하며 실패를 `passed`로 바꾸지 않는다.

## 경계

- 결과물을 만들거나 바꾸는 응답에 적용한다. 검토·감사·검증·완료 판정, 설명·조사만 하는 답에는 적용하지 않는다.
- 코드라면 [Engineering Practices 규칙](../orchestrator/references/engineering-practices/implementation.md) 중 해당하는 것을 적용한다. 주어진 CS 불변조건과 검증 의무를 유지하며, 최소 구현이 CS 검토나 시험 설계를 대신하지 않는다.
- 사용자·프로젝트·저장소 지시(보고 형식, 언어, 시험 위치·도구)가 출력·시험 규칙보다 우선한다. 명시적 비활성화나 사용자 재정의는 이 스킬 전체에 적용되며 자동 선택보다 우선한다. 이후의 명시적 사용은 그 요청에만 적용한다. 스킬이 없거나 꺼져 있으면 멈추거나 다시 켜 달라고 하지 말고 원 요구·수용 기준·필요한 시험을 지킨다.
