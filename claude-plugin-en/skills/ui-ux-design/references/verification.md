# UI/UX 검증과 근거

변경한 결과물과 실제 위험에 맞춰 검증하라. 정적 설계, 결과물 관측, 실제 조작, 사용자 관찰, 자동 검사와 성능 측정을 서로 대체하지 마라.

## 대상 사용자에게 통하는지

매체와 무관하게 이 확인을 먼저 하라. 매체 전용 검사(예: 「화면일 때」 항목)는 해당할 때만 그 뒤에 더한다.

| 확인 | 관측할 결과 |
| --- | --- |
| 첫인상 | 실제 노출 조건(거리·시간·지면·기기·소리 유무)에서 대상 사용자가 처음 알아차리는 것이 핵심 메시지인지 |
| 이해 | 무엇인지, 왜 자신과 관련 있는지, 무엇을 하면 되는지를 대상 사용자가 말할 수 있는지 |
| 행동 | 의도한 다음 행동(문의·구매·길 찾기·작성·구독 등)을 막힘 없이 할 수 있는지 |
| 예외 | 놓침·잘못 읽음·중간 이탈·실패 뒤에도 복구하거나 도움을 찾을 수 있는지 |
| 접근성 | 보기·듣기·읽기·조작에 제약이 있는 사용자도 같은 정보와 행동에 닿는지 |

- 근거 수준을 나눠 남겨라. 검토자의 기준 대조, 노출 조건을 재현한 점검(실제 크기 인쇄본을 설치 거리에서 보기, 소리를 끄고 영상 보기 등), 실제 대상 사용자 관찰은 서로 다르다. 앞의 둘을 사용자 반응으로 보고하지 마라.
- 사용자 관찰에는 참여자 수·조건·과제를 기록하라. 소수 관찰을 전체 효과나 전환율로 확대하지 마라.

## 검증 범위 선택

- 작은 문구·간격 수정에는 해당 결과물과 영향받은 표시 조건부터 확인하라. 요청과 무관한 전체 앱 조사·기기 전수검사·새 시험 체계를 강제하지 마라.
- 설계만 요청받으면 요청한 흐름·상태·조건이 설계안에 반영됐는지 확인하라. 구현·제작하지 않은 결과물을 동작 검증 완료로 표시하지 마라.
- 실제 결과물을 바꿨으면 주요 사용자 동선과 변경으로 깨질 수 있는 경계·실패 상황을 확인하라. 기존 시험과 도구를 우선 재사용하라.
- 사용자나 프로젝트가 정한 시험 서버·환경·권한을 지켜라. 실행 환경이 없으면 가능한 정적 검토를 마치고 실행 검증을 미실행으로 남겨라.
- 핵심 조건을 판단할 수 없는 경우에만 추가 입력을 요청하라. 이미 제공된 결과물·소스·지침·승인을 다시 요구하지 마라.

## 대표 시나리오: 화면일 때

아래에서 해당 변경에 필요한 사례만 선택하고, 이미 있는 결함 사례가 있으면 함께 사용하라.

| 사례 | 관측할 결과 |
| --- | --- |
| 정상 작업 완료 | 진입→선택·입력→실행→결과 확인이 실제 서비스 결과와 일치 |
| 빈 데이터·검색 결과 없음 | 두 상황이 적절히 구분되고 가능한 다음 행동이 드러남 |
| 지연·중복 클릭 | 진행 상태가 유지되고 중복 실행·잘못된 완료 표시가 생기지 않음 |
| 응답 실패·일부 성공 | 유효 입력과 성공한 결과가 보존되며 재시도가 실패 범위와 계약을 따름 |
| 전송 후 응답 단절 | 실패·미실행으로 단정하지 않고 기존 작업 식별자로 결과를 확인하며 변경을 중복 실행하지 않음 |
| 취소·뒤로 가기·재진입 | 취소 범위가 실제 동작과 일치하고 필요한 입력·선택·위치가 유지됨 |
| 세션·검색 조건 빠른 변경 | 늦게 도착한 이전 응답이 현재 화면을 덮어쓰지 않음 |
| 키보드·모달 | 주요 작업이 가능하고 초점이 보이며 모달 열기·닫기 후 위치가 적절함 |
| 작은 창·확대·긴 문구 | 핵심 정보와 행동이 가려지지 않고 읽기·조작이 가능 |
| 한국어 IME·붙여넣기 | 조합 중 의도치 않은 전송·입력 유실이 없고 조합 완료 후 정상 동작 |
| 긴 목록·과거 대화 로드 | 필요한 구간을 읽을 수 있고 기준점·선택·초점이 의도에 맞게 유지 |
| 반복 화면 전환·종료 | 오래된 응답·중복 구독·타이머가 다음 화면에 영향을 주지 않음 |

지원 대상에 모바일·데스크톱이 포함되면 실제 대상의 입력과 창·화면 조건을 확인하라. 브라우저 하나의 확인을 모든 기기·운영체제의 결과로 확대하지 마라. 오류 상태를 확인할 때 허용된 fixture·시험 환경을 사용하고 운영 데이터나 실제 사용자 작업을 임의로 훼손하지 마라.

## 시각·접근성 확인: 화면일 때

- 변경 후보의 실제 화면을 확인할 수 있으면 대표 크기와 관련 상태를 관측하라. 이전 revision의 스크린샷이나 코드 읽기만으로 현재 화면을 확인했다고 하지 마라.
- 겹침·잘림·줄바꿈·시각적 계층·대비·초점 표시와 입력 오류의 전달을 살펴라. 스크린샷은 해당 상태의 외관 근거이며 클릭·키보드·보조 기술 동작의 근거가 아니다.
- 키보드 동선과 동적 초점은 직접 조작하거나 그 동작을 검사하는 기존 자동화로 확인하라. 정적 DOM 존재만으로 동작을 판정하지 마라.
- 자동 접근성 검사, 키보드 확인과 보조 기술 확인의 수행 여부를 각각 남겨라. 한 도구의 통과나 일부 화면 확인을 전체 접근성 준수로 보고하지 마라.
- 수치 기준을 적용하면 목표 표준·수준과 해당 조건을 확인하라. 조건·예외를 생략한 숫자를 모든 텍스트·컨트롤·플랫폼의 공통 기준으로 만들지 마라.

## 반응성과 메모리 확인: 화면일 때

- 실제 문제와 연결된 지표를 고르라. 화면 전환, 초기 표시, 스크롤, 입력 반응, 메모리 사용 중 변경이 영향을 주는 것을 확인하라.
- 데이터량, 대표 조작, 반복 횟수·기간, 실행 환경과 관측 도구를 기록하라. 임의의 보편적 한계값이나 목표치를 만들어 통과 여부를 정하지 마라.
- 비교가 필요하면 같은 조건의 기준판과 후보를 사용하고 측정 범위·변동을 함께 남겨라. 정적 분석이나 다른 환경의 결과로 개선율을 계산하지 마라.
- 메모리 증가를 발견하면 살아 있어야 할 데이터·캐시와 해제되지 않은 참조를 구분하라. 단일 메모리 수치·짧은 관측·가상화 사용만으로 누수 여부를 확정하지 마라.
- 반복 화면 전환에서 요청·리스너·구독·타이머의 수명과 더 이상 필요 없는 화면 자원 회수를 확인하라. 도구가 관측하지 못하는 부분은 추정과 분리하라.
- 관측한 범위에서 이상이 없었다고 보고하라. 실제 장시간·해당 환경 검증이 없으면 무제한 사용 안정성이나 메모리 누수 없음을 보장하지 마라.

## 결과와 실패 기록

- 대상 revision·결과물 또는 경로, 환경, 수행한 조작·검사, 실제 결과와 근거 참조를 연결하라. 비밀이나 불필요한 개인정보를 캡처·공용 기록에 넣지 마라.
- 관찰된 문제, 그 근거에서 도출한 추론과 추가 확인할 원인 가설을 구분하라. 문제가 재현됐다면 사용자 영향의 판단을 불필요하게 약화하지 마라.
- 실행하지 못한 검사는 미실행으로, 실패한 검사는 실패로 남겨라. 스킵·타임아웃·응답 불명을 통과나 결함 없음으로 채우지 마라.
- 수정 후에는 영향받은 사례를 다시 확인하라. 새 위험이나 필수 검사 조건이 없으면 검증 범위를 계속 늘리지 마라.
- 정식 provider 결과의 상태·필드는 [입출력 계약](output-contract.md)을 따르라. 보고서 구조 검사는 실제 사용성·접근성·성능·권한·독립 감사의 참을 증명하지 않는다.
