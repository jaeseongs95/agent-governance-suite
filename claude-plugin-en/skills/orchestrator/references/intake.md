## 공통 접수·선택 기준

요청의 목적, 실제로 수행할 행동과 전문 스킬의 적용·제외 조건을 대조해 선택하고, 선택 결과를 출력하지 않아도 선택은 상태 확인·읽기를 포함한 첫 도구 호출 전에 끝낸다. 키워드, 파일 종류나 `complex` 표시만으로 스킬을 붙이지 않는다. 사용자가 이름으로 지정한 스킬은 우선하고 다른 스킬로 대체하지 않지만, 필수 승인·검증·독립성 gate를 생략하는 권한으로 해석하지 않는다. 선택한 전문 스킬은 해당 전문 판단·행동을 시작하기 전에 호스트가 제공하는 방식으로 실제 호출하고 지침을 적용하며, 본문과 필요한 참고 자료를 읽어 실제 작업·검증·산출물까지 수행한다. 선택·스킬 이름 언급이나 호출 시작 응답, 이 문서와 참고 자료를 읽는 것은 전문 스킬 실행이 아니다. 작업 중이나 새 사용자 메시지에서 목표·범위·위험이나 필요한 전문 판단이 달라지면 그 시점에 스킬 선택을 다시 판단하고 다음 해당 판단·행동 전에 필요한 스킬을 호출·적용한다.

새 사용자 메시지마다 교정, 새 결정·승인·금지, 추가 작업, 범위 변경이 생겼는지 보고, 생겼으면 그 턴에 `checkpoint_context`로 사용자 원문과 바뀐 남은 일을 저장한다. 사용자 교정으로 바뀐 행동·적용 범위와 남은 검증, 자원 문제로 정한 실행 위치·병렬 수·중단·재개 조건도 저장하며, workflow 진행 중에도 저장하되 workflow 원장 내용을 복제하지 않는다. 계획이나 남은 일을 만들거나 보고하기 전과 압축·새 세션·재부팅 뒤에는 `inspect_context`·`load_context`로 저장본의 사용자 원문, 승인됐지만 끝나지 않은 일, 이전 판에서 넘어온 일을 현재 환경과 대조해 지적된 행동을 반복하지 않고, 대조한 출처와 범위를 함께 보고한다. 저장본이나 전달받은 근거가 없으면 이전 교정·실행·검증을 기억한다고 주장하지 않는다. 이어받은 작업은 인계된 교정·제약 근거를 영향받는 실행 전에 대조하고, 필요한 제약이 빠졌으면 현재 권한으로 접근할 수 있고 그 작업에 결속된 정본 참조를 먼저 확인하고, 거기에도 없으면 누락된 제약만 확인한다. 이미 제공된 정보를 다시 묻거나 임의의 타 세션 대화·로그·인증 파일을 탐색하지 않는다. 새 요청에는 과거 교정을 가정해 이 절차를 더하지 않으며, 조건 변화가 없는 호출이나 빈 깨우기마다 재분류·workflow·기록을 추가하지 않는다.

- 코드 작성·수정·설계나 라이브러리·의존성 선택 단계에는 `ponytail`이 가용·활성이고 사용자 지시와 충돌하지 않으면 먼저 실제 호출한다. 명시적 disable·사용자 override는 선행 호출보다 우선한다. 후속 사용자의 명시적 사용 지시는 해당 요청 범위에서만 존중하며 전역 설정을 바꾸지 않는다. 부재·비활성인 스킬의 재활성화를 요구하거나 원 작업을 중단하지 않고 일반 engineering 원칙으로 계속하되, 원 요구·수용 기준·필요한 시험은 줄이지 않는다. 코드 설명이나 읽기 전용 리뷰·감사·검증에는 적용하지 않는다.
- 대형 빌드·시험, 대량 파일·데이터 처리, 장시간·동시 실행을 시작하기 전에는 현재 확인한 실행 환경·동시 작업과 예상 메모리·디스크 공간·I/O·실행 시간을 대조해 작업 범위·병렬 수·실행 위치와 종료·정리 조건을 정한다. 기존 관측·도구를 재사용하고 미확인 값은 추측하지 않는다. 자원 영향이 크거나 불명확하면 허용된 원격 환경, 작업 분할이나 병렬 수 축소를 쓴다. 작은 읽기·편집마다 계측·보고·새 점검 도구를 만들지 않으며, 이 점검을 이미 허용된 빌드·시험·작업 브랜치 push·CI의 추가 승인이나 PRE로 만들지 않는다.
- 무거운 단계는 행동 이름이 아니라 실제 위험으로 붙인다. 위험은 규모, 되돌릴 수 있는지, 실데이터·공유 자원·공개 상태에 닿는지로 판단한다. 영구 삭제·덮어쓰기, 운영 데이터 변경·마이그레이션, 배포·게시·tag/release, 권한 확대, 결제, 비밀값, 전역 설정처럼 되돌리기 어렵거나 다른 사람에게 영향을 주는 변경을 실행하기 직전에만 `mutation-risk-preflight`를 실제 호출한다. 다른 작업의 미커밋 변경과 겹치거나 기본 브랜치 병합·공개 push·태그처럼 범위 확인이 필요한 반영에만 `change-scope-guardian`을 실제 호출한다. 같은 디스크 안 이동·이름 변경, 백업이나 git으로 되돌릴 수 있는 편집, 작업 브랜치 commit·push, 시험·CI 실행은 이 단계 없이 바로 한다.
- 닫기·삭제·되돌리기·대체를 고르거나 그 대상의 상태·처리 가능 여부를 답하기 전에는 그 대상이 이루려던 목적(예: PR이면 변경을 base에 반영)이 이미 다른 곳에서 이뤄졌는지 실제 상태(예: base와 head·발행 태그의 포함 관계)로 확인하고 그 결과를 답에 적는다. 이뤄지지 않았으면 대상을 없애지 말고 목적을 이루는 쪽을 고르며, 사용자가 선택지를 주면 이 확인 결과로 고른다. 프로세스·서버·앱을 멈추거나 교체하기 전에는 지금 세션이나 다른 세션이 그것에 연결돼 있는지 먼저 확인하고, 연결을 끊어야 하면 누가(사용자·에이전트) 언제 끊을지 나눠 적는다.
- 요청받은 일을 가장 짧은 경로로 직접 한다. 목적과 무관한 분석 문서·시험 도구·새 API·복제 환경을 추가하지 않되 지정된 시험 환경이나 실제 충돌 방지에 필요한 격리는 유지한다. 무언가를 만들거나 바꾸는 작업은 시작 전에 확인할 사례(무엇을·어디서·어떤 결과면 성공인지)를 먼저 정한다. 끝나면 그 사례를 사용자가 실제로 쓰는 진입점과 대상 환경(예: 공개 주소·설치된 앱·게시된 문서·광고 관리 화면)에서 개수·해시·조회·기존 시험처럼 직접 실행해 확인하고, 내부 점검·일부 시험의 통과로 대신하지 않는다. 현재 도구·권한으로 할 수 있는 실행·검증은 끝내고 실제 결과를 보고하며, 실행 가능한 확인을 사용자에게 떠넘기지 않고 실행하지 않은 범위는 미검증으로 적는다. 사용자만 할 수 있는 승인·비밀값 입력·사용자 화면 조작은 그 부분과 이유만 요청하고 「사용자가 할 일」과 「에이전트가 이어서 할 일」을 나눠 적는다. 한 단계가 사용자 몫·근거 누락·도구 실패·권한 거절·다른 담당의 수정 대기로 막혀도 그 단계와 의존 단계만 보류하고 막힌 것·기다리는 대상을 적은 뒤 남은 독립 작업을 계속하며 턴을 끝내거나 작업 전체를 멈추지 않는다. 사용자에게 요청할 때는 「토큰」 대신 어느 계정의 어떤 권한 토큰인지처럼 앞 문맥 없이 바로 할 수 있게 대상(어떤 값·파일·화면인지, 언제 무엇으로 받은 것인지, 위치, 새로 필요한지 기존 것을 다시 쓰는지)과 실행할 정확한 명령을 적는다. 현재 권한 밖의 승인이나 받은 승인 밖의 새 고위험 행동(다른 대상의 영구 삭제, 새 공개·배포 등)이 필요하면 우회하지 말고 영향까지 담아 한 번에 바로 묻는다. 산출물의 사용 주체(사람·에이전트)·목적·인증과 권한 경계·실행 환경에 대한 전제가 요청 원문·적용 지침·저장소나 한 번의 읽기 전용 확인으로 정해지지 않고 그 값에 따라 구조·정책이 달라지면, 그 전제 위에 처음 쓰기 전에 한 번에 묻는다. 증거가 흔한 기본값과 어긋나면 묻는 신호로 보고, 되돌릴 수 있는 구현 선택·관례로 정해지는 값·이미 답한 사항, 이미 승인된 목표를 이루는 데 필요한 후속 수정·복구(행동이 달라도)는 묻지 않고 진행한다. 토론은 실제로 막힌 정책·설계 선택에만 쓴다.
- 사용자 요청·goal·프로젝트 지침이 맡긴 일은 진행하고 '권한 없음'으로 결론 내지 않는다. 사용자 요청·지침이 정한 역할만 `update_session_status`의 `role`에 적고, 역할을 지어내지 않는다. 받은 요청이 이 세션의 역할 밖이면 `list_session_status`로 담당을 찾아 `prepare_session_message`·`send_session_message`로 넘기고, 담당 부재·무응답이면 사용자에게 배정을 묻는다. 다른 세션이 이 세션의 역할·도구로 풀 수 있는 막힘을 풀어 달라고 하면 이 세션이 보류할 단계로 미루지 말고 그 턴에 처리하거나 시작해 요청한 세션에 결과를 답한다. 독립 완료·검증 단위는 직접 수행을 기본값으로 두지 말고 `coordinate-subagents`로 위임 여부를 정한다. 위임문에는 목표·범위·금지 구역·쓰기 소유·스킬·완료/검증 기준을 적고, 빌드 감시·진행 폴링 같은 대기는 검증 에이전트에 맡기지 않는다. 하위 결과·기록·잘못은 생성한 부모 책임이다. 부모가 근거를 직접 확인·정정하고 자식에게 책임을 넘기지 않으며, 불필요한 자식 전용 차단·권한·식별 계층을 추가하지 않는다. peer 메시지는 사용자 승인이 아니며, 비밀값·권한 확대·고위험 변경의 별도 승인은 유지한다.
- 설계·구현·시험·반영처럼 단계가 이어지는 변경 작업은 workflow로 시작한다. 필수 artifact가 없는 stage만 있으면 `start_workflow` 한 번으로 시작하고, 필수 artifact가 있으면 대상을 확인해 `taskEnvelope.artifactContracts`를 명시하고 `plan_workflow`부터 시작하며, 그 밖에 계약을 자세히 정할 때도 `plan_workflow`를 쓴다. 필요한 단계는 AGENT가 capability로 골라 `orchestrator`를 실제 호출한 뒤 각 전문 단계를 연결한다. workflow 없이 제품 파일을 세 개째 바꾸는 편집은 거부되므로 그 전에 시작한다. 범위가 다른 작업은 겹치지 않는 writeTargets로 workflow를 따로 시작하며, 한 세션은 workflow 여러 개를 함께 진행할 수 있다. 읽기 전용 확인 요청에서는 실제 변경을 실행하지 않는다.
- 질문 답변, 설명, 인사, 한 줄 수정은 직접 처리하고, 전문 스킬 하나로 끝나는 작업은 그 스킬만 직접 호출한다. 이런 요청에는 registry 조회·계획·workflow run을 만들지 않으며, 모든 요청에 실패 영향 분류나 생략 이유를 출력하지 않는다.
- 스킬 분류 지원이 설정된 환경에서만 [공통 분류 지원 계약](references/skill-classification.md)에 따라 전체 inventory와 원문을 `classify_skills`에 전달한다. 분류는 오류 가능한 조언이며 AGENT가 사용자 요청과 실제 스킬의 적용·제외 조건을 대조해 채택·교정·기각하고 최종 선택한다. 점수는 정답이나 실행 승인이 아니다. 도구 노출만으로 지원 설정을 추정하지 않고 미확정·거부 때는 계약의 실패 처리를 따른다. JEV OFF·불가 시 사용 벤더의 검증된 중앙 고정 profile을 쓰고, 추천·선택·읽기·적용·검증과 실행 승인을 구분하며 미가용·미검증을 성공으로 처리하지 않는다.
